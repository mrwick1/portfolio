bare vs Chrome: a measured baseline

One real end-to-end test on a staging web app, run in Chrome and in bare, on the same machine and the same minute. This is the baseline that later work is measured against.

IThe test

The app is a production Next.js and React dashboard for a voice-AI product, on its staging server. The test does what a QA engineer does by hand:

  1. Log in.
  2. Create a client.
  3. Create an agent for it with a three-step wizard: setup, name and voice, review.
  4. Delete the agent.
  5. Delete the client.

Both browsers run the same step file. bare runs it with bare-drive. Chrome runs it through a small driver over the DevTools protocol, the same protocol that Playwright uses. The Chrome driver sends real mouse events and waits until an element stops moving before it clicks. After every run, a script checks the app and finds no test data left behind.

IIITime and CPU

bare finishes the journey 1.25x faster and uses 1.3x less CPU time. Most of the CPU gap is in the kernel. Chrome spends 9x more kernel time on starting processes and passing messages between them.

Where bare is slower. bare runs 17% more user-space instructions than Chrome. This app is mostly React and app scripts. Chrome compiles JavaScript with V8. At the time of this test, bare walked the syntax tree and had no JIT. bare now runs JavaScript in Vex, its own bytecode interpreter. On a small static test page in an earlier comparison, bare used 250x fewer instructions. On a script-heavy app, the JavaScript engine is the gap to close.

VIMethod and limits

One machine: AMD Ryzen 9 5900HX, 16 threads, Linux 7.2. Each browser ran in its own cgroup. CPU time and memory peaks come from the cgroup, user instructions from perf stat, and PSS from a sampler every 20 ms. Window runs used an isolated headless Wayland compositor, so no run touched the desktop.

Before the runs, I paused every other workload on the machine: other agents, 29 containers, a virtual machine, timers and file sync. Load average stayed between 0.3 and 0.9. The runs alternated between the two browsers, 6 pairs headless and 4 pairs in a window.

Not tested. A second machine, more runs, a real desktop window, a warm Chrome cache between runs (each Chrome run used a fresh profile), and Playwright itself. Wall times depend on the network and the staging server. The instruction counts are the most repeatable numbers.
