Checking generated UI against Figma

A local tool for comparing a generated interface with its Figma source.

Tags
Figma AI Agents Tooling

ISmall differences

I use coding agents for an initial implementation of interfaces. The result often resembles the design while missing details that matter during review.

Those differences can be hard to find by eye.

Padding, font weight, corner radius, and gradient stops can each differ slightly. I was checking them by opening the design and browser side by side.

The agent could read design properties and produce code, but it lacked a reliable check of the rendered result.

I built figma-connect to provide that feedback. Its verification function is verify_node.

IIThe verification step

verify_node renders the candidate code in a browser and compares it with the matching Figma node. It returns a result with a difference image.

The tool also reads geometry, auto-layout, fills, typography, tokens, and components. Verification adds a check on what the implementation actually renders.

The tool runs locally and supports Figma in the browser. Its plugin and local bridge provide design access without using the Figma cloud REST API.

IIIHow the Check Actually Works

The check takes a node ID and candidate code. It renders the code in Chromium through Playwright, exports the Figma node, and runs several comparisons.

Pixel differences catch shifts, shapes, and colours, but even a small global offset can affect many pixels. I also use SSIM for structural similarity and text and accessibility checks with axe-core.

The output labels the expected image, actual image, and difference. This gives the reviewer a visible explanation alongside the score.

The agent can use that result to revise the implementation before requesting review.

IVReliable captures

The main challenge was making captures consistent enough to trust. A failure caused by capture timing should not be mistaken for an implementation defect.

Some early failures came from capturing the page before web fonts loaded. Waiting for document.fonts.ready removed that source of mismatch.

Waiting for networkidle also caused problems on pages with persistent connections. I replaced the blanket wait with explicit readiness checks.

The node summary has a limited size, so it cannot include every property at full precision. Fidelity flags identify how gradients, shadows, strokes, opacity, and masks are represented.

VImplementation

A Figma plugin reads the document. A local bridge indexes its data in SQLite and exposes it through MCP. A separate harness renders and compares the candidate code. A stdio adapter connects the agent to the bridge. The project has about 15k lines of TypeScript and 35 tools; the bridge binds to localhost.

VIWhat It Still Can't Do

The tool has limits that affect how I use its results.

Search matches layer names and text rather than semantic meaning. The node summary is budgeted, with fidelity flags for its limits. The tool does not write changes back to Figma.

The goal is a useful review loop: render the implementation, inspect the differences, and revise it against the design.
